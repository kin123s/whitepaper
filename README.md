# Whitepaper Collection

> **실무에서 AI를 쓰다 보니, 결국 시스템을 만들게 되었다.**
>
> *규칙 파일 하나에서 시작해, Knowledge Graph까지 — 한 엔지니어의 1년간의 진화 기록.*

---

## 왜 이걸 만들게 되었나

2025년, AI 코딩 에이전트(GitHub Copilot, Claude, Cursor)를 실무 프로젝트에 본격 도입하면서 하나의 질문이 계속 돌아왔다.

> *"AI한테 어떻게 하면 우리 코드베이스의 맥락을 더 잘 전달할 수 있을까?"*

처음에는 단순했다. `copilot-instructions.md`에 규칙 몇 줄 적고, 프롬프트를 잘 쓰면 되겠지 싶었다. 하지만 레거시 PHP 20만 줄, 10년치 DB 스키마, 3개 프로젝트를 넘나드는 현실 앞에서 그건 금방 한계에 부딪혔다.

AI가 존재하지 않는 테이블 컬럼으로 SQL을 만들고, 어제 알려준 규칙을 오늘은 잊어버리고, 프로젝트 A의 규칙을 프로젝트 B에서 무시했다. 이런 문제들을 하나씩 해결하다 보니 — 규칙을 계층화하고, 토큰 예산을 관리하고, 검색을 강제하고, 지식 그래프로 연결하는 — **하나의 시스템**이 만들어졌다.

이 시리즈는 그 과정을 단계별로 기록한 것이다. 각 챕터는 독립적인 결과물인 동시에, **이전 챕터의 한계가 다음 챕터의 시작점**이 되는 연속된 여정이다.

---

## 진화의 여정

```
문제 발견                 아키텍처 설계             현실과의 충돌            다음 단계로
"AI가 맥락을 잊는다" → 3-Layer 규칙 시스템  →  "레거시가 너무 복잡하다"  →  Ch.2
                                                     ↓
"규칙만으론 부족하다"  →  MCP RAG Server    →  "벡터 검색의 한계"       →  Ch.3-2
"검색할 곳이 없다"     →  (직접 구축)       →  "Multi-hop 쿼리 실패"    →  GraphRAG
```

### Chapter 1. AI Agent Governance Architecture
#### *"규칙을 만들었다. 그런데 AI가 검색할 곳이 없었다."*

AI 에이전트에게 어떻게 규칙과 컨텍스트를 전달할 것인가 — 이 질문에서 출발한다.
`copilot-instructions.md` 하나로 시작했지만, 토큰 한도·컨텍스트 유실·프로젝트 간 불일치가 반복되었다.
결국 규칙을 **L1(전사) / L2(프로젝트) / L3(태스크)** 세 계층으로 분리하고, Hub-and-Spoke 동기화 구조를 설계했다.

> **이 챕터의 끝에서 발견된 한계:**
> 규칙 안에 "DB 스키마를 추측하지 말고 검색하라"고 써봤는데 — *검색할 곳이 없었다.*

### Chapter 2. Legacy Modernization
#### *"검색 인프라를 만들기 전에, 코드베이스 자체가 문제였다."*

AI에게 "우리 코드를 이해해줘"라고 하려면, 먼저 그 코드가 **이해할 수 있는 구조**여야 했다.
200,000줄의 PHP, 파일명이 곧 URL인 라우팅, 문자열 결합 SQL — 기존 시스템을 그대로 두고서는
AI도, 신규 기능 개발도 한계가 있었다. "전부 다시 만들자"는 유혹을 뿌리치고
**Strangler Fig 패턴**으로 레거시를 멈추지 않으면서 3-Area 하이브리드 아키텍처를 병행 운영했다.

> **이 챕터의 끝에서 발견된 한계:**
> 코드베이스를 정리했지만, AI가 34,000개 파일을 실시간으로 "알고 있을" 방법이 없었다.
> *검색 인프라를 직접 만들어야 했다.*

### Chapter 3. MCP RAG Server → GraphRAG
#### *"검색 인프라를 만들었다. 그러나 벡터 검색만으로는 부족했다."*

Ch.1의 "검색하라" 원칙을 실현하기 위해 MCP 서버와 벡터 검색 인프라를 직접 구축했다.
GPU가 없는 사내 서버에서 CPU 경량 모델, TF-IDF 폴백, 스텔스 인덱싱을 조합했다.
하지만 벡터 검색은 **"이 함수가 어떤 클래스에서 호출되는가"** 같은 관계 추적에 취약했다.
결국 Neo4j 기반 Knowledge Graph를 도입해 34,678개 파일, 198,205개 함수를 노드로 구성하고
**Triple-Hybrid 검색(Vector + Keyword + Graph)** 으로 진화했다.

> **이 챕터가 보여주는 것:**
> 기술 선택은 "무엇이 최신인가"가 아니라 **"지금 환경의 제약이 무엇인가"** 에서 결정된다.
> 그리고 충분히 쓰면, 한계가 보이고, 다음 구조가 필요해진다.
